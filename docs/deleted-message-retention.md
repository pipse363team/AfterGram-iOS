# Telegram 13.0: сохранение удалённых сообщений

Основа — официальный `release-13.0.0`, commit `f1dd7a2dbd02cbbf513e75d5695d8d36d1cf5838`.
Это модифицированный, неофициальный клиент. Остальные функции WhiteGram сюда не перенесены.
Исходный WhiteGram сохранён в локальной ветке `master`.

## Что изменено

- При удалении загруженного облачного сообщения оно остаётся в своей позиции в чате.
- Сообщение отображается с opacity `0.5`; под ним — иконка корзины и «Удалено».
- Текст, GIF, видео, видеосообщения и фотографии используют общий механизм сохранения.
- Удалённые элементы альбома отделяются от остальных, чтобы не затемнять весь альбом.
- Повторная сверка истории с сервером тоже сохраняет исчезнувшие сообщения.
- Метка записывается в Postbox, а полные медиа — в `MediaBox.basePath/retained-message-media`, вне обычного кэша.
- Сохранённое медиа использует штатный `LocalFileMediaResource`; при очистке кэша воспроизводится из отдельной копии.
- Медиа отображаемых сообщений скачиваются заранее, по два ресурса одновременно. Загрузки принадлежат аккаунту и продолжаются после ухода сообщения с экрана.
- Настройки → «Удалённые сообщения» позволяют отключить последующее сохранение и предварительную загрузку.

## Принцип

В опубликованной ветке WhiteGram `db18308774f863074278feedc4df4507b0fb174e` механизма anti-delete нет.
Её `DeletedMessagesView.swift` и обработчик удалений совпадают с исходным Telegram 12.6.2:
view сообщает об удалённых ID, а текст и медиа удаляются обычным способом.

Новая реализация перехватывает `.DeleteMessagesWithGlobalIds` и `.DeleteMessages` в
`AccountStateManagementUtils.swift`, сохраняет доступные медиа и добавляет
`RemotelyDeletedMessageAttribute` вместо удаления строки. Физическое удаление и его
события применяются только к остальным ID. `HistoryViewStateValidation.swift` использует
тот же механизм. Ручное удаление пользователем продолжает работать обычным способом.

Скачанный файл сохраняется атомарно через hard link с fallback на копирование.
При воспроизведении `Fetch.swift` ищет отдельную копию по ID локального ресурса.
Путь вычисляется от текущего каталога аккаунта, а не от старого абсолютного пути контейнера.

## Ограничения и статус проверки

- Нельзя восстановить сообщение, которое клиент никогда не загрузил.
- Если удалённый файл не успел скачаться и сервер уже его не отдаёт, просмотр не гарантируется.
- Предварительная загрузка начинается для сообщений, отрисованных в чате, а не для всей истории всех чатов.
- Файлы требуют места и трафика. Отдельные копии не входят в обычную очистку кэша Telegram; удаление строки сообщения не очищает все резервные файлы. Они удаляются вместе с данными аккаунта/приложения.
- Секретные чаты, запланированные сообщения и массовое удаление истории через `min_available_id` не покрыты этой реализацией.
- Команды сервера для уже удалённого сообщения могут быть недоступны; это локально сохранённая запись.
- На Linux проверены синтаксис изменённых Swift-файлов относительно исходной версии, YAML, shell-скрипт, подготовка конфигурации и отсутствие ошибок в diff.
- Компиляция iOS и XCTest здесь НЕ выполнялись. IPA НЕ собран. Реализация требует проверки на macOS и iPhone.

## Сборка с Windows через GitHub Actions

1. Загрузить подготовленные изменения поверх указанного официального тега в свой GitHub-репозиторий.
2. Получить собственные `api_id` и `api_hash` на https://my.telegram.org/apps.
3. Добавить их в Settings → Secrets and variables → Actions как `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`.
4. Открыть Actions → **Telegram 13.0 with retained messages** → Run workflow.
5. После успешного выполнения скачать artifact `TelegramRetention-13.0`.

Workflow использует macOS 26, Xcode из `versions.json` (26.6), Bazel 9.2.0 и запускает
`DeletedMessageRetentionTests` перед сборкой. Можно отключить запуск тестов во входных параметрах.
IPA подписывается ad hoc для последующей переподписи; для установки на iPhone нужна
подпись подходящего Apple ID/сертификата через выбранный инструмент установки.
Расширения и Watch-приложение в этой сборке отключены. Push-уведомления зависят от
профиля, которым будет переподписан IPA. Workflow не публикует релизы и не делает push.

## Проверка на устройстве

Отправить со второго клиента текст, GIF, обычное видео, видеосообщение и фото.
Открыть их в этой сборке и дождаться полной загрузки. Удалить со второго клиента для всех.
Проверить прозрачность 50%, значок снизу и воспроизведение. Затем перезапустить приложение,
перейти к старым сообщениям, очистить обычный кэш и повторить просмотр без сети.
Отдельно проверить альбом, повторное удаление, ручное удаление сохранённой записи,
переключение аккаунтов и отключение функции. Неполностью загруженное видео не должно
показываться как гарантированно сохранённое.
