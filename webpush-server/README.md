# AfterGram notification bridge

This service receives incoming Telegram events from the private MTProto bridge. When ntfy is configured, it publishes to the owner’s self-hosted ntfy server and includes an `tgretention://open?...` click route. It sends only to ntfy in this mode, so existing Web Push subscriptions do not receive duplicates. If ntfy is not configured, the older Web Push delivery remains available.

The iOS ntfy app receives the push through ntfy’s iOS relay. The relay gets the hash of the private topic and a generic wake-up marker; the iPhone then downloads the actual notification from the personal server. Telegram message text, chat IDs, and click routes stay on the personal server.

## Enable ntfy on the VPS

Deploy the current repository files to `/opt/aftergram-webpush`, then run this once on the Debian/Ubuntu VPS:

```sh
sudo bash /opt/aftergram-webpush/webpush-server/setup-ntfy-server.sh
```

The script installs ntfy from its official apt repository, reuses the server’s existing IP TLS certificate, creates a random 256-bit topic, configures a one-hour message cache and the required iOS relay, opens TCP port `9444` in UFW if it is active, and restarts the existing notification API. It keeps anonymous access denied except for that single random topic. The topic itself acts as the access secret; anyone who gets it can read and publish on that topic, so keep it private.

If the VPS provider has a separate firewall, allow inbound TCP port `9444` there. The setup page will not show the private topic until the owner enters the existing API token.

Then on the iPhone:

1. Install the [ntfy iOS app](https://apps.apple.com/app/ntfy/id1625396347) and allow its notifications in iOS.
2. Open the AfterGram notification setup page and enter the existing owner API token. The page remembers it in local storage on this device, as before.
3. In ntfy, add server `https://144.31.165.8:9444`, then subscribe to the private topic shown by the page.
4. Tap **Send a test notification** on the setup page. Once that arrives, tap a real Telegram notification to test its route into AfterGram.
5. After ntfy is working, tap **Turn off old Web Push notifications** on the setup page to remove the previous subscription and stop duplicate alerts.

ntfy’s click URL supports app-specific URIs, but its documentation says the responsible app *may* open. The final check is a real notification tap on the target iPhone with AfterGram installed. If iOS opens ntfy but not AfterGram, notification delivery is working and the remaining issue is custom-URL handling in the ntfy iOS client.

## Start

Use Node.js 20 or later. Set these environment variables in the server's service manager, not in Git:

```sh
WEBPUSH_API_TOKEN=<random secret of at least 32 characters>
WEBPUSH_SUBJECT=mailto:<real contact address>
WEBPUSH_ALLOWED_ORIGIN=https://pipse363team.github.io
WEBPUSH_DATA_DIR=/var/lib/aftergram-webpush
HOST=127.0.0.1
PORT=8788
NTFY_SERVER_URL=https://144.31.165.8:9444
NTFY_TOPIC=<generated by setup-ntfy-server.sh>
```

Install and start behind an HTTPS reverse proxy. The process binds to `127.0.0.1`; expose only the proxy's HTTPS port. Keep the data directory readable only by the service account and back up `vapid-keys.json` securely. If the key is lost, existing subscriptions must be recreated with the new public key.

```sh
npm ci
npm start
```

For a direct TLS listener, set `WEBPUSH_TLS_CERT` and `WEBPUSH_TLS_KEY` to readable certificate files and bind the selected public HTTPS port with `HOST=0.0.0.0`. The repository includes `aftergram-webpush.service` as the current VPS systemd example; it reads its bearer token from `/etc/aftergram-webpush.env` and uses systemd credentials for the TLS private key.

The configured VPS endpoint is `https://144.31.165.8:9443`, using the server's short-lived Let's Encrypt IP certificate. Certbot renews the certificate automatically; install `aftergram-webpush-certbot-deploy.sh` as a deploy hook so the service reloads the renewed certificate. The API token is stored root-only in `/etc/aftergram-webpush.env`; retrieve it on the server with `sudo grep '^WEBPUSH_API_TOKEN=' /etc/aftergram-webpush.env` and enter it in the PWA setup page. Do not put that token in the repository or share it publicly.

## API

- `GET /healthz` — health check.
- `GET /v1/vapid-public-key` — legacy Web Push public key.
- `GET /v1/ntfy-config` — private ntfy server and topic settings; requires the owner bearer token.
- `POST /v1/subscriptions` — save a browser subscription. Requires `Authorization: Bearer $WEBPUSH_API_TOKEN`.
- `POST /v1/unsubscribe` — remove a subscription by `{ "endpoint": "..." }`. Requires the same bearer token.
- `POST /v1/send` — send `{ "title": "...", "description": "...", "custom": { "peer_type": "user|group|channel", "peer_id": "...", "message_id": "..." } }`. With ntfy configured it publishes through ntfy and adds the AfterGram route. Without ntfy it uses the legacy Web Push subscriptions. Requires the same bearer token.

The API token must be entered only on the owner's device and must not be embedded in GitHub Pages JavaScript. A production setup needs a private pairing step or a reverse proxy that authenticates the owner before allowing subscription writes and sends.

## Telegram integration

The Telegram bridge uses a separate MTProto user session and listens only to incoming new messages. It checks Telegram’s per-chat mute setting and suppresses messages from chats that are muted. It sends the sender/chat title, message text (or a media label), peer type, peer ID, and message ID to this server. Message contents and the login session are not logged. With ntfy enabled, tapping the alert asks iOS to open the matching AfterGram chat directly through the existing `tgretention` URL handler.

### Personal Telegram account setup on the VPS

1. Create Telegram `api_id` and `api_hash` at <https://my.telegram.org> → API development tools. Telegram requires third-party clients to use their own API credentials and comply with its API terms.
2. From an SSH terminal, run `sudo /usr/local/bin/aftergram-telegram-login`. Enter the API credentials, phone number, Telegram login code, and optional two-step password at its prompts. The helper saves the API credentials in a root-only environment file, stores the session under `/var/lib/aftergram-telegram` with mode `0600`, and starts the systemd service. Do not copy the session or API hash into Git or chat.

The service can only start receiving messages after the account owner completes that interactive login. Telegram may show the new third-party client under Devices. Revoke it there to stop access immediately. The bridge does not send messages or change account data.
